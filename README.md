# Harnes — референсный харнесс

База знаний для развёртывания рабочего окружения агента под конкретный проект.
Здесь лежат разделы `backend/`, `frontend/` и `shared/`: скиллы, инженерные принципы
и шаблоны конфигов. Рабочий `.dsh/` проекта **собирается из этой базы копированием** —
база не является проектом и не подключается к нему ссылками.

Чего здесь намеренно нет: ролей и процесса конкретных проектов («кто архитектор»,
«кто исполнитель», `ai-tasks`, отчёты, ревью микро-задач, git-конвенции). Это свойства
проекта, а не инженерная база; они живут в `.dsh/AGENTS.md` самого проекта.

## Структура

```
Harnes/
├── README.md               # этот файл
├── AGENTS.md               # правила работы с базой
├── MIGRATION.md            # журнал переноса: что взято, что нет и почему
├── PLUGINS.md              # справочник плагинов DSH: название и назначение
├── shared/                 # работает и в бэкенде, и во фронтенде
│   ├── skills/             # 26 скиллов: дисциплина разработки, ревью, домен, писательство
│   └── README.md
├── backend/                # .NET: архитектура, данные, API, тесты, тулинг
│   ├── principles/         # инженерные принципы (reference)
│   ├── skills/             # 8 скиллов: dotnet/skills (4) + SQL Server (Microsoft Learn, 4)
│   ├── templates/          # шаблоны конфигов сборки
│   ├── sources.md          # официальные источники скиллов и что из них брать
│   └── README.md
├── frontend/               # React + TypeScript: структура, данные, UI, качество
│   ├── principles/
│   ├── skills/             # 5 скиллов: vercel-labs/agent-skills (React, UI, тексты)
│   ├── templates/
│   ├── sources.md
│   └── README.md
└── scripts/
    ├── install-skills.ps1  # раскладывает набор из базы в <проект>/.dsh/skills
    ├── verify-library.ps1  # проверяет frontmatter, имена и ссылки во всех скиллах
    └── fetch-sources.ps1   # клонирует официальные наборы в _vendor/ (нужна сеть)
```

## Как развернуть харнесс под проект

1. Скопировать нужные разделы в проект: `backend/` для серверной части, `frontend/` —
   для клиентской, `shared/` — в обоих случаях.
2. Разложить скиллы в проект:

   ```powershell
   # только общие + бэкенд
   .\scripts\install-skills.ps1 -Project H:\path\to\project -Set shared,backend

   # только общие + фронтенд
   .\scripts\install-skills.ps1 -Project H:\path\to\project -Set shared,frontend
   ```

   Скрипт копирует каталоги `<name>/SKILL.md` в `<проект>/.dsh/skills`. Плоская раскладка
   обязательна: DSH читает ровно один уровень вложенности (`skills/<name>/SKILL.md`),
   подпапки вида `skills/backend/...` он не видит.
3. Взять принципы раздела как основу `.dsh/AGENTS.md` проекта: убрать неприменимое,
   дописать проектную специфику. Принципы — вход, а не готовый файл проекта.
4. Шаблоны из `templates/` положить в корень сборки бэкенда (`Directory.Build.props`,
   `Directory.Packages.props`, `.globalconfig`, `global.json`, `.gitignore`) и подставить
   свои версии пакетов.
5. Официальные наборы скиллов подтянуть скриптом `scripts/fetch-sources.ps1` (список
   источников — в `sources.md` разделов).

## Правила базы

- **Один смысл — одно место.** Скилл, принцип, шаблон живут в одном разделе; копии
  в проектах — расходный материал, а не источник правды.
- **Раздел определяет принадлежность.** Работает в обоих стеках → `shared/`; знает про
  слои, БД, ASP.NET → `backend/`; знает про React, браузер, вёрстку → `frontend/`.
- **Официальное — вендорим, локальное — не тащим.** Скиллы из официальных источников
  лежат копиями с указанием источника и даты; самодельные скиллы под процесс проекта
  в базу не попадают.
- **Версии пинятся точно.** Плавающих версий и `latest` в шаблонах нет.
- **Чужая лицензия остаётся чужой.** Вендоренный скилл приходит вместе с лицензией
  источника; она фиксируется в `SOURCE.md` и переносится в проект вместе со скиллом.
  Текст скилла не переписывается: расхождение с официальной линией оформляется отдельным
  блоком отклонения с причиной и датой.
- **Глобального — минимум.** В пользовательском `~/.dsh` остаётся только подключение
  моделей и данные сессий; правила и скиллы живут в базе (разделы) или в проекте
  (`.dsh/`). Настраивать окружение через `~/.dsh/skills` не нужно.

## Проверка базы

```powershell
# все разделы
powershell -ExecutionPolicy Bypass -File .\scripts\verify-library.ps1

# один раздел
powershell -ExecutionPolicy Bypass -File .\scripts\verify-library.ps1 -Set frontend
```

Проверяются признаки, из-за которых DSH молча пропускает скилл: наличие `SKILL.md`,
frontmatter с `name` и `description`, совпадение имени с папкой, незакавыченное двоеточие
в значении, битые относительные ссылки. Вендоренный набор `shared/skills` дополнительно
проверяется на целостность: `shared\skills\verify-set.cmd` (сверка SHA-256 с манифестом).

## Заметки по окружению

- Инструмент DSH запускает команды в **Windows PowerShell 5.1** (не `pwsh` 7),
  поэтому в inline-командах держите ASCII: кириллица в тексте команды искажается ещё
  до запуска дочернего процесса.
- Русский текст в скриптах — только в файле `.ps1`, записанном в **UTF-8 с BOM**:
  PowerShell 5.1 читает `.ps1` без BOM как ANSI и превращает кириллицу в мусор.
- Сеть: `curl.exe` работает — им и качаются официальные наборы (`codeload` + `tar`).
  `git clone` из песочницы падает на TLS (`schannel: SEC_E_NO_CREDENTIALS`), а
  `Invoke-WebRequest` — на приёме ответа. Поэтому загрузчик по умолчанию идёт через `curl`,
  а `git` доступен флагом `-UseGit`.
- Агент правит файлы поштучно (`write`/`edit`), а не через `Set-Content`/`-replace`:
  массовая правка необратима и не оставляет следа, что именно изменилось.
- Внутри каталога скилла не должно быть `AGENTS.md`: DSH читает его как инструкции
  каталога и грузит в контекст, дублируя `SKILL.md`. Скомпилированные `AGENTS.md`
  из официальных наборов в базу не вендорятся.
